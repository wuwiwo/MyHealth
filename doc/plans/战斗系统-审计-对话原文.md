# MyHealth 战斗系统重构与全链路修复任务书

## 0. 任务定位

你是本项目的 **Lead Commander / Battle System Technical Lead（主指挥、架构负责人、验收负责人）**。

你的职责不是亲自承担全部代码编写，而是：

1. 全面理解当前 Battle System。
2. 分析现有问题、根因、依赖关系。
3. 将工作拆解为明确、可执行、可验证的任务。
4. 指挥其他 AI / Coding Agent / Executor 实现代码。
5. 对执行结果进行代码审查、测试审查和行为验收。
6. 必要时要求执行者返工。
7. 最终确保战斗系统达到"规则一致、行为正确、日志正确、UI一致、测试可验证"的状态。

### 核心原则

> **先理解系统，再修改系统；先修根因，再修表象；先建立统一规则，再继续扩展功能。**

禁止采用"看到一个 Bug 就局部打补丁"的工作方式。

本任务的最终目标不是简单修几个已知 Bug，而是：

> **修复当前 Battle System 的高优先级错误，并建立统一、可维护、可测试的战斗执行链路，避免同类 Bug 持续发生。**

# 4. P0：必须首先修复

## P0-1 Battle Exception 不得判定玩家胜利

重点检查：

```text
page/game-battle.js
```

特别检查：

```js
runBattle()
battleTick()
```

当前存在的危险行为：

```text
battleTick() exception
        ↓
enemy.hp = 0
        ↓
done = true
        ↓
winner = true
        ↓
endBattle(true)
```

这类行为必须彻底禁止。

### 正确行为

Battle Engine 出现未处理异常：

```text
battle error
    ↓
battle aborted / error
    ↓
停止战斗
    ↓
不得产生正常胜利
    ↓
不得发放胜利奖励
    ↓
不得推进正常通关状态
    ↓
保留完整错误信息
```

至少记录：

```text
battle id
battle mode
round
phase
actor
target
skill
error stack
```

### 验收

必须增加测试：

```text
人为制造 battleTick exception
→ 战斗不得判定玩家胜利
→ 不得进入正常奖励流程
→ 错误必须可追踪
```

## P0-2 AI Target 必须真正进入 Cast Pipeline

重点检查：

```text
page/ai.js
page/battle-group.js
page/skill.js
```

当前链路可能是：

```text
AI Decide
    ↓
选择 skill
    ↓
选择 target
    ↓
target 被丢弃
    ↓
castSkill()
    ↓
重新 selectTargets()
```

这属于严重逻辑错误。

### 要求

AI 的：

```js
aiDecide()
```

返回的：

```text
skillId
target
skillDef
```

必须与实际执行路径连接起来。

建议方向：

```js
castSkill(gb, actor, skillId, {
    forcedTargets
})
```

但具体 API 必须由 Codex 根据现有架构设计。

### 注意

不能简单强行所有技能都使用 AI target。

必须区分：

```text
单体技能
AOE
Self
Ally
Random Enemy
Random N Enemies
Lowest HP
Taunt
特殊目标规则
```

也就是说：

> AI Target 是"声明的目标决策"，Skill Targeting Rule 是"技能自身的合法目标规则"。

两者必须兼容，而不是互相覆盖。

### 验收

必须增加 End-to-End 测试：

```text
AI 决定 Target A
→ castSkill
→ 实际受影响 Target 必须为 A
```

至少覆盖：

```text
攻击低 HP 敌人
治疗低 HP 队友
Taunt
Boss Skill
普通攻击
```

禁止只测试：

```text
aiPickTarget()
```

而必须测试：

```text
aiDecide()
→ action declaration
→ cast
→ actual target
```

# 6. 建立统一 Damage Resolver

最终目标：

所有"真正造成伤害"的行为都应该经过统一 Damage Pipeline。

建议建立类似：

```js
resolveDamage({
    attacker,
    target,
    amount,
    damageType,
    source,
    skill,
    isAoe,
    canCrit,
    canBlock,
    canShield,
    canReflect,
    canLifesteal,
})
```

最终接口可以不同。

重点不是函数名字。

重点是：

> **所有伤害必须拥有一个统一的权威结算路径。**

# Enemy Group Battle Presentation & UI Diagnosis Report

## 0. Executive Summary

### 核心结论

当前 MyHealth 敌群战斗**并不是"没有做 UI"**。

实际上已经存在相当多的表现层：

* 战场化上下对阵布局
* 行动顺序条
* 当前行动者高亮
* 受击抖动
* 伤害 / 治疗飘字
* 技能中央特效

* 状态图标
* 战斗日志
* 日志筛选
* 战斗 / 日志双 Tab

* 战斗速度 1× / 2× / 4× / 8×
* 单位详情
* 敌人头像
* 宠物头像
* 战斗统计

问题恰恰在于：

> **这些表现功能是不断叠加出来的，而不是围绕一个统一的 Combat Presentation Model 建立的。**

当前系统的本质仍然是：

```text
Battle Engine
    ↓
修改 Unit State
    ↓
生成 Battle Log
    ↓
game-render.js 重新 render 整个 Battle Overlay
    ↓
再从 Log 文案中解析发生了什么
    ↓
推测应该播放什么动画
```

也就是说：

> **Engine 已经是结构化战斗系统，但 Presentation Layer 仍然部分依赖"从人类可读日志猜事件"。**

这是目前"逻辑能跑，但不像一个完成度高的战斗系统"的最核心架构原因。

# 1. 当前敌群战斗表现架构

当前实际链路可以还原成：

```text
startGroupTrial()
        │
        ├── createUnit()
        ├── createEnemyUnit()
        ├── createGroupBattle()
        │
        ▼
   Group Battle Engine
   page/battle-group.js
        │
        ├── runPhasePrepare()
        │
        ├── buildActionQueue()
        │
        ├── runUnitActionStep()
        │       │
        │       ├── groupUnitTurn()
        │       │
        │       ├── normalAttack()
        │       │
        │       ├── castSkill()
        │       │
        │       └── playerAttackSkill()
        │
        ├── runPhaseJudge()
        │
        └── runPhaseEnd()
        │
        ▼
    gb.events / gb.log
        │
        ▼
    _groupStep()
    page/game-render.js
        │
        ├── groupBattleStep()
        │
        ├── renderGroupOverlay()
        │       └── innerHTML = entire battle UI
        │
        ├── playAttackFeedback()
        │       └── gbParseHit()
        │             └── Regex parse log text
        │
        └── gbShowSkillCast()
                └── bubble event
                      ↓
                   #gbFx
                      ↓
                CSS Animation
```

当前 Engine 本身已经具备比较完整的阶段结构：

```text
Prepare
  ↓
Action
  ↓
Judge
  ↓
End
```

而且 `groupBattleStep()` 已经把"一次行动"拆成了单单位推进，因此非常适合未来建立真正的 Presentation Queue。

# 2. 当前 Engine 的表现驱动方式

## 2.1 Engine State

存在。

例如：

```text
gb.turn
gb.phase
gb.done
gb.winner
gb._stepQueue
gb._stepIdx
```

并且行动队列可以直接提供：

```text
当前行动者
下一行动者
剩余行动单位
```

这是非常好的基础。

---

## 2.2 Battle Log

也存在，而且非常丰富。

例如事件拥有：

```js
{
    msg,
    targetId,
    type
}
```

甚至日志条目还有：

```js
{
    turn,
    unit,
    events,
    phase
}
```

这已经接近一个真正的 Combat Event 系统。

---

## 2.3 DOM State

表现层大量依赖 DOM。

`renderGroupOverlay()` 每次行动都会：

```text
重新生成整个 Battle Overlay
↓
ov.innerHTML = h
↓
重新绑定所有事件
```

这是当前表现系统的重要技术债。

---

## 2.4 setTimeout

大量存在。

例如：

```text
700 / speed
900 / speed
500ms
400ms
500ms
900ms
```

因此当前战斗表现实际上属于：

> **State Step + DOM Rebuild + Timeout Animation**

而不是：

> **Combat Event → Presentation Queue → Animation Timeline**

# 3. 最严重的架构问题

## P0-1：UI 通过解析日志文本判断"发生了什么"

这是当前最值得优先处理的问题。

`playAttackFeedback()` 并不是收到：

```js
{
    type: "damage",
    sourceId,
    targetId,
    amount,
    damageType,
    crit
}
```

而是拿到：

```text
Battle Log
↓
msg 字符串
↓
正则
↓
猜测这是伤害
```

例如：

```js
dmgSkill
dmgPlain
rock
bolt
reflect
recoil
selfsac
dot
heal
shield
```

然后：

```js
gbParseHit()
```

再决定：

```text
是不是伤害？
多少？
是不是暴击？
应该给谁闪？
应该生成什么数字？
```

这就是典型的：

> **Presentation Layer Reverse Engineering the Battle Engine**

而不是 Engine 主动告诉 Presentation：

> "这里发生了一次 1432 点暴击伤害。"

---

# 4. 更严重：部分事件甚至没有统一 type

这是实际源码中非常重要的问题。

例如 `playerAttackSkill()` 的陨石、冰魄、巨石事件主要生成：

```js
{
    msg: '☄️ ... 陨石轰炸 ...'
}
```

而不是统一的：

```js
{
    type: 'damage',
    targetId,
    amount,
    ...
}
```

因此 `gbParseHit()`：

```text
e.type === damage
```

才能进入伤害解析。

结果：

```text
普通攻击
→ 有 type
→ 有机会产生受击反馈

部分敌群技能
→ 有 type
→ 有机会产生反馈

部分玩家技能
→ 没有 type
→ Presentation Layer 根本不知道这是一次 Damage Event
```

这不是单纯的"动画少"。

这是：

> **Combat Event Contract 不完整。**

# 5. 为什么现在的攻击"没有打击感"

当前普通攻击大致是：

```text
Engine:
HP -= damage
↓
生成 damage log
↓
renderGroupOverlay()
↓
playAttackFeedback()
↓
目标 gb-hit
↓
伤害数字
```

视觉上缺失：

```text
攻击者准备
↓
攻击意图
↓
攻击者动作
↓
攻击方向
↓
攻击瞬间
↓
Impact
↓
受击
↓
Hit Stop
↓
伤害数字
↓
收招
```

当前真正存在的主要是：

```text
目标抖动
+
数字
```

因此玩家的感知实际上是：

> "某个单位的 HP 数字发生变化。"

而不是：

> "这个单位攻击了那个单位。"

这正是任务书要求重点诊断的 Game Feel 问题。

# 18. 自动战斗速度问题

当前：

```text
1×
2×
4×
8×
```

对应大约：

```text
700ms
350ms
175ms
87.5ms
```

这是当前表现系统的一个关键矛盾。

因为 Animation 本身仍然大约：

```text
400ms
900ms
```

例如：

```text
Hit = 400ms
Damage Float = 900ms
Skill Cast = 900ms
```

所以：

### 1×

可以勉强观看。

### 2×

开始出现动画重叠。

### 4×

：

```text
新的行动
↓
旧伤害数字还没消失
↓
新技能特效覆盖
```

### 8×

：

```text
87.5ms
```

已经远小于：

```text
400ms / 900ms
```

所以不是：

> "动画速度变快。"

而是：

> **事件产生速度远远超过 Presentation Layer 的消费能力。**

# 19. 当前最大的节奏问题

现在实际上是：

```text
Engine Event Rate
        ↓
        ████████████████

Presentation Capacity
        ↓
        ████
```

所以越高速：

```text
信息越多
↓
动画越重叠
↓
数字越多
↓
玩家越看不懂
```

因此：

> **高速模式绝对不能只是把 setTimeout 除以 8。**

任务书中对此的要求是正确的：高速模式必须决定哪些表现保留、缩短、合并、跳过。

# 20. 当前真正的根因

可以归纳为 7 个层级。

## Root Cause A — 没有 Presentation Event Contract

Engine 已经有：

```text
type
targetId
msg
```

但还没有真正的：

```text
sourceId
targetIds
actionId
skillId
amount
damageType
hitIndex
hitCount
crit
shieldAbsorbed
statusId
```

---

## Root Cause B — UI 解析人类可读日志

当前：

```text
Log Message
↓
Regex
↓
猜测 Event
↓
Animation
```

应该变成：

```text
Combat Resolution
↓
Structured Combat Event
↓
Presentation
```

---

## Root Cause C — Render 与 Animation 没有解耦

当前：

```text
groupBattleStep()
↓
renderGroupOverlay()
↓
playAttackFeedback()
```

而 `renderGroupOverlay()` 会：

```text
innerHTML = 整个战场
```

因此 Presentation Layer 被 DOM Render 生命周期绑死。

---

## Root Cause D — 没有 Animation Queue

当前更接近：

```text
Event
↓
立即播放
```

需要变成：

```text
Combat Events
↓
Presentation Events
↓
Priority
↓
Grouping
↓
Queue
↓
Animation
```

---

## Root Cause E — 没有 Action Semantics

目前：

```text
Attack
Skill
Heal
Buff
Debuff
AOE
Death
```

没有完整的视觉动作语言。

---

## Root Cause F — 高速模式没有真正的 Presentation Policy

当前主要是：

```text
delay /= speed
```

而不是：

```text
Presentation Quality Policy
```

---

## Root Cause G — 死亡不是 Presentation Event

死亡目前只是：

```text
HP = 0
↓
CSS grayscale
```

而应该是：

```text
unitDeath
↓
death presentation
↓
death confirmation
```

# 23. 推荐的新 Presentation Architecture

最终建议：


## 2. 但它说"已有动画全部被重建杀死"，这个表述过度了

这是我认为这份审计最需要修正的地方。

### `.gb-hit` 并没有被立即杀死

当前 `_groupStep()` 的顺序是：

```js
var step = groupBattleStep(_groupBattle)

if (step.unit) _groupActing = step.unit.id

renderGroupOverlay(false)

if (step.unit) playAttackFeedback(_groupBattle, step)
```

也就是说：

1. 先重新渲染 overlay
2. 再执行 `playAttackFeedback()`
3. `playAttackFeedback()` 在**新 DOM**上执行：

```js
card.classList.add('gb-hit')
setTimeout(..., 500)
```

因此 `.gb-hit` 是可以实际播放的。

它不是"被 innerHTML 重建完全打死"，而是：

> **它依赖"每步重新生成 DOM → 重新加 class"的脆弱机制。**

所以这里正确的技术表述应该是：

**"全量重建使需要依赖 DOM 连续性的动画/transition 失去连续状态，其中 HP transition 是确定失效；hit 动画仍能播放，但动画生命周期与渲染生命周期耦合。"**

这是和"全部动画失效"有明显区别的。

---

### `.gb-acting` 也不是完全失效

当前 CSS 明确存在：

```css
.gb-unit.gb-arena-unit.gb-acting{
  transform:scale(1.1);
}
```

而且还有：

```css
.gb-unit.gb-arena-unit.gb-acting::before{
  animation:gbActingPulse 1.1s ease-in-out infinite
}
```

所以当前行动者的：

* 放大
* 光环
* 左侧强调条
* Pulse

都还是存在的。

它的问题不是"完全不能用"，而是：

> **行动状态是通过每次 render 重新创建 chip 后重新挂 class 来维持，缺乏连续状态。**

所以二审说"重建是打击感问题的核心根因"是对的，但说成"已有动画基本全部失效"是不准确的。

# 3. 它指出 `GB_FX_SLOT_OFF` 的机制，我确认是正确的

这部分很扎实。

源码：

```js
var GB_FX_SLOT_OFF=[
  [0,0],
  [-46,-18],
  [46,-18],
  [0,-36]
]
```

而：

```js
function playAttackFeedback(gb, step) {
  ...
  var slot = 0
  evs.forEach(...)
}
```

所以：

> **每一个行动步骤都会从 `slot = 0` 开始重新编号。**

也就是说，同一个 step 最多只有：

```text
slot 0
slot 1
slot 2
slot 3
```

四个空间位。

超过四条以后：

```js
slot % 4
```

会重新使用位置。

同时，下一步又重新从 slot 0 开始。

因此"飘字重叠"不是泛泛的"消费能力不足"，而是几个具体因素叠加：

**固定 4 槽 + 每 step 重置 + 飘字寿命 900ms + 事件生产频率高于动画消费速度。**

这一点二审比第一份报告精准很多。
