## 3. 双方分歧与最终裁决

### 3.1 分歧一：表现层「失效」的范围

| | 主张 |
|---|---|
| 本地初版 | 「每步全量重建，**杀死所有 CSS 过渡**」，并在对话中写过「**所有动效都被降级成了硬切**」 |
| #5 二次审计 | 该表述**过头**：`.gb-hit` 能实际播放（因 `_groupStep` 先 `renderGroupOverlay`、后 `playAttackFeedback`，class 加在**新 DOM** 上）；`.gb-acting` 的放大/光环/强调条/Pulse 也都还在 |

**裁决：本地认错一半，#5 的替代表述反而更粗。**

- ✅ **本地认错**：对话中那句「所有动效都被降级成了硬切」确实过头。准确分层见 §2.4-S4。
- ⚠️ 但本地审计**表格内**的原始表述是量化的、正确的：「`gb-hit` … 下次重建时被销毁：×1 播完 100%、×2 87%、×4 44%、×8 22%」。
- ❌ **#5 用二元判断替换了量化判断**：它只说「可以实际播放」，丢掉了「×8 只播完 22%」这个唯一有操作意义的事实。
- ❌ **#5 关于 `.gb-acting` 的纠正是稻草人**：本地原文写的是「`scale(1.1)` **瞬跳**」，讲**没有过渡**，不是「没有状态」。
- ✅ **#5 的执行顺序观察有价值**：`renderGroupOverlay` → `playAttackFeedback`，`.gb-hit` 加在新 DOM 上。本地原文未把顺序讲这么清楚，**采纳**。

### 3.2 分歧二：AI target 是否已修（**本轮最重要的分歧**）

| | 主张 |
|---|---|
| #5 二次审计 | 当前 `main` 已有 `if (actTarget) targets = [actTarget];` 与 `predeclareActions`，故「算出 AI target 但完全没传进去」**已不是现状**；本地拿它当 P0 属**时效性错误**，并据此给本地「对当前 main 的时效性 6.5/10」 |
| 本地 | 该主张**不成立** |

**裁决：❌ #5 不成立。它只验了普攻分支就下了全称判断。**

1. **本地从未主张「完全没传」**。本地原始判定即写明：「⚠️ **部分属实**：技能路径确实丢目标，但普攻路径 `:1698` **用了** `actTarget`」。#5 把本地**已经承认的那一半**当作反证。
2. **技能路径至今仍丢目标**（当前 HEAD `9234255` 复核）：
   ```js
   // battle-group.js:1690
   var castEvents = castSkill(gb, actor, skillId);   // ← 未传 actTarget
   // battle-group.js:802（castSkill 内部）
   var targets = selectTargets(gb, actor, def);      // ← 重新选目标，AI 决策被丢弃
   ```
3. **`battle-group.js` 自 `c429e4b`（v2.4.8）起未再改动**，该 commit 早于双方审计的全部 commit → **不存在时效性问题，双方看的是同一份代码**。
4. **`predeclareActions` 不能作为反证**：它的用途是**决定出手顺序**（`unitPriorityRank` 分档），`takeDeclaredAction` 把 target 交回后技能路径照样丢弃。预声明的存在恰恰**反证**了该缺陷 —— 它算出的 target 在技能路径上无人接收。
5. **#5 据此给出的「时效性 6.5/10」建立在错误前提上 → 作废。**

### 3.4 分歧四：跳过行动触发额外行动（#1 §18）

**裁决：❌ #1 定级错误 —— 这不是缺陷，是作者已裁定的口径。**

`affix.js:226-228` 原文：「⚠️ **口径边界（如实记录，未改）**：判定点是『本单位本回合的行动结束』，与修前一致 —— 被冰冻/畏缩/慢启动**跳过行动**的单位同样会走到这里，故它也有 55% 的『额外行动』（那一次额外行动仍然什么有效的事都不做，只多一条『无法行动』日志）。」

`#1` 把「改设计」包装成「修 P2 缺陷」，违反其自身 §31「不得自行脑补」。**若要改，须走作者裁决流程，不得当作 bug 修。**

## 7. 建议施工顺序

> 原则：**先修正确性 → 再让已有表现生效 → 最后补缺失演出**。
> 理由：表现层做得再好，演出的仍是错的结算；且 #1/#3 的「先建整套 Presentation Architecture」会让
> 上述 P0 在漂亮动画下更难被发现。

### 阶段 1 — 正确性 P0（必须先做）

1. `game-battle.js:155-162` 异常不得判胜；异常须留完整上下文（battleId / round / phase / actor / stack）并可追踪。
2. `playerAttackSkill` 三个技能接入统一伤害结算路径（含命中/暴击/格挡/护盾/减伤/反伤/吸血/死亡判定），并改用 `effectiveStat`。
3. 陨石改为**无放回抽样**（契约 `design-v2.0.md:71/390`）。

### 阶段 2 — 表现基础（性价比最高）

4. 特效时长改为跟随速度（`900/speed`），槽位**跨步递增**而非每步重置。
5. 广场改为**按 `uid` 复用元素、只改 `style`/`class`** 的局部更新，使 `transition` 真正生效。
   ⚠️ 入口仍须是 `renderGroupOverlay`（守住 `test-group-ui-presentation.js:420-424`）。
6. 给 `.gb-arena-unit` 补 `opacity` 过渡（消除每步频闪）。
7. 把 `playAttackFeedback` 与 `gbShowSkillCast` 拆到两个时间片，建立「施法 → 结算」节奏。

### 阶段 3 — 正确性 P1

8. 技能路径把 AI target 传入 `castSkill`（须兼容单目标/AOE/self/ally/随机/嘲讽等既有目标规则，**不得互相覆盖**）。
9. 单敌事件方向语义化（引入 source/target/side，勿只交换 `if`）。
10. 单敌护盾/吸血/词条口径统一（**先裁决**，见 §8）。
11. overkill 吸血口径统一。

### 阶段 4 — 表现补强

12. attacker motion（复用单敌 motion language，不照搬实现）、hit flash、hit stop、death animation、crit/AOE/multi-hit 表现。

### 阶段 5 — 抽象（最后）

13. Presentation Event / Queue / Speed Policy。
    ⚠️ 现有 `gbParseHit` / `playAttackFeedback` / `gbShowSkillCast` / `#gbFx` / `#gbArenaMid`
    已构成一个**边界很差的半成品表现层** —— 目标是**收窄边界**，不是推倒重建。

## 10. 结论

1. **#1 任务书**：问题识别部分正确，但存在**编造设计依据**（§5.2）、**双引擎盲区**（S1）、**两条错误定级**（E15/E17）、**版本过期**（V1）。不可直接施工。
2. **#3 表现诊断**：**确实读过源码、零编造**，对表现层的根因判断（R1~R7）基本成立；但把 R1 只当性能技术债、未推出「已实现的过渡因此失效」，且方案偏重。
3. **#5 二次审计**：对**表现层**的复核合格；对**引擎正确性**的复核不合格（只验普攻分支即宣布技能路径 P0 已修 = 假阴性；未查设计文档即要求重开陨石契约）。其「时效性 6.5/10」作废。
4. **双方最终建议实为一致**：先修正确性 → 再修表现基础 → 最后抽抽象。
5. **可立即开工的 P0 三条**（§7 阶段 1）与**须先裁决的 7 项**（§8）已分离，不存在阻塞。
