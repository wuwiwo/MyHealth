# MyHealth 战斗体验设计提案 v1

> **状态：设计阶段提案，待作者确认；不是已批准的实现规格。**
> **范围：**重整现有单敌与敌群战斗的演出、战斗反馈、胜负收尾、单场复盘与长期统计体验；不设计新战斗规则。
> **本次交付：**仅设计文档，不改运行代码、版本号、缓存戳、README 版本栏或 changelog。
> **事实基线：**现行代码为唯一现状依据。单敌与敌群是两条独立的战斗引擎及渲染管线；不得用一条管线的验收冒充另一条。
> **提案标记：**下文的体验目标和数字阈值是供作者确认的可测默认值，未确认前不视为已裁决，不据此擅自修改玩法、奖励或数据持久化。

---

## 1. 游戏愿景

让移动端 MyHealth 玩家在完成训练后，通过挑战获得一场**看得懂行动与结果、能感受到关键状态变化、结束后能快速复盘并理解长期进步**的 RPG 战斗体验；表现强化必须忠实呈现既有结算事实，不改变战斗结果。

**本提案解决的问题**

- 结算、奖励反馈在战斗结束时并发，注意力被分散。
- 有单位卡、行动横幅、飘字、日志与部分状态徽标，但玩家仍难连续辨认“谁行动、影响谁、发生了什么”。
- 当前有单场群战摘要，但挑战记录没有形成可浏览的战斗历史与趋势。

**设计原则**

1. 先保信息含义与阅读节奏，再做炫目效果。
2. 动画表达已发生的战斗事件；视觉效果不能暗示未发生的命中、暴击、治疗、状态或击杀。
3. 自动快进与逐帧阅读是不同观看模式；速度提高时收缩表现密度，不牺牲结果摘要。
4. 同一体验目标分别落实并验收于单敌与敌群管线。
5. 统计是可追溯的数据视图；口径不确定或无法归因的数据不伪装成精确值。
6. 尊重用户对奖励、收尾和数据留存的裁决；未决项先记录，不先写成实现承诺。

## 2. 核心体验循环

这是**现有挑战循环的体验改造**，不是新增战斗玩法：

1. **选择挑战**：玩家从当前已有入口选择单敌关卡或敌群小关；查看现有关卡与战斗信息。
2. **进行战斗**：引擎照常结算；表现层以行动者、目标和结果为主线呈现关键事件。玩家可以使用该模式已有的手动/自动推进与速度控制。
3. **确认胜负**：先识别战斗已经结束及胜负结果；此时不同时要求玩家阅读长统计表或奖励细项。
4. **确认战果**：按确认后的产品顺序查看奖励及通关变化；奖励展示不得与结算信息争抢同一时刻的注意力。
5. **复盘与继续**：打开单场摘要/战报；在确认的历史记录范围内比较表现，再选择下一关、重试或返回。

> 第 3–5 步是提案中的流程目标。奖励与结算的确切先后、是否需点击确认、自动模式能否自动继续，均为作者待裁决项（见第 8–9 节）；在裁决前不得将本图当成已定交互规格。

## 3. 目标用户与平台

- **目标用户**：使用 MyHealth 记录健身并体验 RPG 挑战的个人玩家；主要在手机上进行，兼容桌面浏览器。
- **运行形态**：现有纯前端单页应用、单人回合制挑战；不引入联网对战或服务器权威战斗。
- **设备与输入**：触屏优先，同时兼容鼠标/键盘可用的网页交互。触控热区继续遵循项目现有设计规范。
- **性能目标（提案，待确认）**：在项目当前支持的移动端浏览器上，360×640 与 390×844 视口不出现横向溢出、核心单位信息不被裁切、面板互相遮挡或浏览器控制台错误；演出不得阻塞战斗继续推进。暂不承诺 60fps 等尚未量测的帧率数字。
- **可访问性**：动画不能是理解事件的唯一通道；需同时提供可读文本/徽标/日志，支持减少动态效果的系统偏好（实现前检查现有支持与影响）。

## 4. 范围

下列 P0 是**提案的产品优先级**，不表示本次已施工。每项先给可验证的通过条件；阈值带“建议值”的均须作者确认后成为正式验收门槛。

### P0：本专题体验必须达成

| 特性 | 设计要求 | 可验证验收标准（建议值，待确认） |
|---|---|---|
| P0.1 行动—目标—结果可读 | 玩家能从一次关键行动的呈现辨认行动者、受影响单位、结果类别及结果值/状态；表现锚定正确目标。 | 对单敌和敌群分别选取至少 10 个真实战斗事件（含伤害、治疗/护盾、状态变化、击杀/终局；若某类关卡不可触发须注明），至少 8/10 的受测者在日志不展开时正确指出行动者、目标与结果；事件日志与引擎事件逐项对应，错误目标反馈为 0。**样本与 80% 门槛为提案值。** |
| P0.2 状态与护盾即时反馈 | 对已知状态施加/刷新/净化/抵抗/结束以及护盾吸收/破碎，提供语义不同、目标明确的瞬时提示；持续状态可由单位当前标记辨认。未知事件不猜测、不制造反馈。 | 为状态与护盾事件制作“结算事件→表现”映射表；自动化覆盖表内 100% 已支持事件，未知/目标缺失事件不错误挂载；真实浏览器中每类至少演示一个可触发实例，且即时反馈目标与事件 `targetId` / side 一致。 |
| P0.3 按速度组织反馈 | ×1 优先逐事件阅读；更高速档聚合可安全合并的重复结果，保留主要行动、目标、总结果与重要状态/击杀。两个目标或不同语义不得错误合并。 | ×1、×2、×4、×8 的自动化测试分别验证事件顺序/合并口径；引擎日志、HP、胜负和 RNG 输出与基线完全一致（纯表现修改）；真实浏览器每档均无目标误绑、数字与日志冲突、FX 无限残留。具体每档停留时长、并发 FX 上限待裁决并实测后登记。 |
| P0.4 胜负、奖励、结算不再抢读 | 终局先清楚表达胜/败；奖励、通关进度和战绩按一条经作者确认的顺序呈现；每个阶段有明确进入/离开动作或明确自动行为。 | 浏览器录制/自动化验证单敌胜利、单敌失败、敌群胜利、敌群失败四条路径：胜负结果均先于详细战绩呈现；奖励消息不与结算面板同时争抢焦点；一次战斗奖励/进度只结算一次；确认流程后下一步行为唯一、可预测。顺序细节待作者裁决。 |
| P0.5 单场战绩能解释表现 | 单场复盘优先回答“结果如何、贡献来自哪里、关键转折是什么”，并提供可继续查看的战报；现有字段只有在口径可靠时展示。 | 为单敌和敌群分别定义字段字典、归因规则与已知缺失；用固定种子真实战斗核对 UI 每个数值等于所定义事件集合的合计；无事件/不可归因时明确显示 0、未知或不适用，不误导为精确贡献。单敌统计范围及跨管线字段对齐待设计裁决。 |
| P0.6 战斗记录与统计入口 | 玩家能够从挑战的“记录”视图查看战斗相关表现，而不需要从训练 PR 或单场结算中猜测长期变化。 | 如批准持久历史：至少能保存并浏览最近战斗的日期、模式、关卡、结果与一组已裁决指标；页面能正确区分没有历史和统计为零，跨刷新数据一致。保留数量、字段、同步/导出策略及旧数据策略须先裁决，不预设具体数据模型。 |
| P0.7 不让演出遮挡或改变玩法 | FX 不遮挡必要信息、日志或操作；不改变伤害、目标、状态时序、胜负、掉落与随机序列。 | 在两个模式、360×640/390×844、抽屉开/关、×1/2/4/8 实测：关键信息遮挡/裁切为 0，触控操作可达；固定种子日志、结果、HP、RNG 与基线逐项一致。 |

### P1：后续迭代（不阻塞 P0）

- 经用户确认后加入音效、震动、镜头/舞台特效；静音和系统减少动态效果偏好须同步设计。
- 更多历史图表、关卡热度图、队伍/宠物构筑对比、可筛选战报。
- 分享复盘卡片、战斗回放或时间轴重播；不在首次改造里扩大数据范围。
- 长期体验研究后再调整奖励动画、自动连战节奏或失败后建议。

### 明确不做

- 不改伤害公式、命中/暴击契约、技能/状态规则、AI、关卡难度、奖励数量、胜负判定或 RNG。
- 不合并单敌与敌群引擎，也不以改动一套模式代替另一套模式的验收。
- 不为“动画不明显”简单增加全屏粒子、摇屏、颜色闪烁或同时播放音效；不让装饰效果压过目标信息。
- 未经裁决不新增强制点击步骤、不取消用户已有控制、不改变自动模式推进/连战语义。
- 未经裁决不保存完整逐步引擎日志、不改云同步/导入导出协议、不增加无限增长的历史存档。
- 不以插画/新头像/资源采购作为 P0 前置；复用现有单位、宠物、怪物、技能图标与视觉令牌。

## 5. 关卡与内容规模

- 仅针对现有挑战内容与事件，不新增关卡、Boss、敌人、技能、状态或剧情。
- 当前内容规模以运行时配置为准：单敌关卡来自 `page/levels.js`，敌群来自 `page/group-levels.js`。文档历史记录中的章数/大关数可能滞后，不在本提案重述易过期数字。
- 每条渲染管线至少选普通战斗与可触发特殊机制的战斗做浏览器验收；尽量覆盖多目标、护盾、治疗、状态、击杀及环境伤害。若内容无法稳定触发某项，以固定种子或明确标为该路径未验证。
- 战斗事件视觉映射应按**事件语义**而非硬编码关卡名设计；关卡配置只作为验收样本。

## 6. 美术与音频

- **方向**：移动端可读的轻量 RPG 战斗舞台。重点采用行动焦点、目标受击、血条变化、单位状态变化和终局转场来表达因果；保留项目现有深/浅色主题与令牌体系。
- **素材**：优先复用现有怪物头像、宠物头像及技能图标；动效以 CSS/DOM 轻量实现为主。缺少资源时可用简洁的程序化形状或文本标记，不因素材缺口阻断核心信息反馈。
- **音频/震动**：本期 P0 不依赖；是否加入、默认开关、浏览器权限及无声环境体验均待确认。
- **动效约束**：普通事件短且克制；重大事件有层级但不长时间锁住操作；系统减少动态效果时仍能读懂战斗结果。具体时长和振幅需要原型实测，不在文档阶段臆定像素/毫秒常数。

## 7. 输入方案

| 输入 | 动作 | 设计约束 |
|---|---|---|
| 触屏点击 | 选择关卡、切换战斗/日志、手动推进、改变速度、打开/关闭复盘 | 沿用现有入口；新增流程不可误触跳过奖励或复盘；关键按钮热区遵循项目规范。 |
| 鼠标点击 | 与触屏对应的网页控件操作 | 不依赖悬停才出现的关键信息。 |
| 键盘 | 使用现有可聚焦控件的原生激活方式（Enter/Space）；若后续需战斗快捷键，另行裁决 | 焦点可见且顺序合理；不发明未实现快捷键。 |
| 系统偏好 | `prefers-reduced-motion`（若接入） | 关闭非必要位移/闪烁后仍保留行动者、目标、结果、状态及胜负文字。 |

> 本专题不新增战斗操作种类；手动/自动和速度档位的行为以现有模式为基线。收尾新增确认按钮与否待裁决。

## 8. 风险登记与开放问题

| 风险 / 开放问题 | 影响 | 对策 / 状态 |
|---|---|---|
| 表现“更明显”变成画面更拥挤 | 无法辨认目标和结果，复现原问题 | 先做事件层级与反馈容量规则，再做美化；以关键事件辨认率和遮挡测量验收。 |
| 高速合并丢失语义（例如不同来源伤害、不同目标、护盾与 HP） | FX 与真实结算不一致 | 合并键必须基于目标及事件语义；详细数字/日志继续可查；固定种子验证展示与引擎事件一致。 |
| 单敌和敌群事件模型不同 | 一套“修好”而另一套仍缺反馈 | 分模式列事件映射、分别做浏览器验收；公共规范统一语义，不强行共用引擎或事件结构。 |
| 当前战报存在归因限制（敌群 `gb.log` 行动者按名字归因，同名单位无法完全区分） | MVP、输出/治疗贡献可能归错人 | 历史统计立项前决定是否补稳定 `unitId` 事件元数据；未补前同名归因披露限制，不把估算称为精确。 |
| 单敌与敌群统计口径不能直接比较 | 跨模式趋势失真 | 先分别定义指标与分母；仅比较有共同定义的指标，否则分开展示。 |
| 是否持久保存战斗历史、保存哪些字段、保留多久 | 存储增长、隐私/同步兼容、旧存档迁移复杂度 | **待作者裁决**；优先考虑有界摘要而非完整日志，正式方案需另列 schema、容量上限、迁移、导出/同步策略。 |
| 结算与奖励先后、是否点击确认、自动模式是否暂停/继续 | 改变玩家现有流程与自动连战行为 | **待作者裁决**；在流程裁决前只制作可点击原型/流程稿，不落代码。 |
| 用户体验阈值尚未验证 | 指标门槛可能过严或不足 | 80% 辨认率、样本量、移动端视口为提案默认值；原型测试后由作者定案并记录测试条件。 |
| 依赖动效表现的用户可能受减少动态设置影响 | 可访问性模式反馈不足 | 动画之外始终保留文本、状态标记、HP/战报；减少动态效果需纳入同一验收。 |

### 待裁决清单（本提案不擅自定案）

1. 终局流程采用“胜负 → 奖励 → 战绩”的分步顺序，还是“胜负 → 战绩（内含奖励）”？奖励何时实际入账？
2. 用户是否必须点击继续？自动战斗/自动连战时，是否自动经过阶段、停留多久、能否一键跳过？
3. 胜负表现、奖励展示与详细战绩是否共用一个面板，还是分步面板/阶段？战斗场景需不需要在复盘期间保留？
4. 统计是否跨会话持久化？保存最近多少场、保存摘要还是完整日志？是否纳入手动导出/云同步？
5. P0 长期统计最重要的指标是哪几个？建议候选：场次/胜率/连胜、平均回合数、我方造成伤害/治疗/承伤、场地/DOT 伤害；是否要按模式分开展示？
6. 是否接受关键事件辨认测试“至少 8/10 正确”的建议门槛，以及每模式至少 10 个事件样本的测试方法？
7. 音效、触觉反馈与 `prefers-reduced-motion` 支持是否纳入本轮实施，还是排入后续版本？

## 9. 技术约束与完成自检

### 技术约束

- **不更换引擎**：现项目是原生 JavaScript + HTML/CSS 的浏览器 SPA，没有独立游戏渲染引擎。纯 UI 演出继续使用现有 DOM/CSS；必要时评估少量 Canvas，但不能把它作为信息可读性的替代。
- **保持依赖边界**：单敌逻辑为 `page/battle.js` + `page/game-battle.js`；敌群逻辑为 `page/battle-group.js` + `page/game-render.js`。纯表现任务不得更改引擎输出；两套管线需要各自的测试与浏览器样本。
- **事件为事实源**：展示只消费引擎产生的日志/事件，不从动画反推伤害，也不通过 UI 改变结算。事件缺少稳定目标/来源标识时，先明确兼容和数据模型方案。
- **统计数据**：单场即时结算统计与跨场历史统计分层。长期数据需先定 schema 版本、迁移、保留上限及云同步/导出边界，不能在表现改造中顺带静默扩写存档。
- **浏览器验收**：使用现有测试体系及真实 Chromium；至少覆盖两个模式、窄屏、速度档位、日志抽屉状态、浅/深主题与减少动态效果（若支持）。页面隐藏时布局测量无效，浏览器夹具须先进入挑战页并打开战斗视图。
- **施工阶段门槛**：本提案通过后再拆施工任务。任何线上代码改动须按 `AGENTS.md` bump `APP_VERSION`、同步版本文档与缓存戳、跑测试并提交；本次设计稿本身只按 `docs:` 提交。

### 拷问清单（答案与待定项）

- **一句话能说清体验吗？**能：看懂行动因果、感受到关键状态、结束后能复盘与看见进步。
- **MVP 最小到只剩什么仍有价值？**明确行动者/目标/结果、让状态和护盾变化可读、让终局不并发抢读、提供可信的单场摘要。长期趋势是 P0 目标但需先裁决持久化范围；若用户不批准存档变更，第一阶段只能做会话内或现有进度可支持的视图，不得假称已交付历史趋势。
- **每个 P0 都可验证吗？**可；表中逐项给出行为、统计、遮挡、基线一致性等条件。数值阈值需作者确认后冻结。
- **是否把锦上添花误列 P0？**音效、震动、镜头特效、分享回放明确放 P1；不作为核心体验依赖。
- **平台与输入是否匹配？**是；移动优先浏览器，沿用点按、现有手动/自动推进和速度控制；新增流程不依赖悬停或键盘快捷键。
- **哪些决定还答不上？**结算/奖励阶段顺序及确认交互、自动模式收尾策略、历史存档与同步范围、核心长期指标与模式比较口径、验收样本阈值及音效/减少动态效果范围；全部列为待作者裁决，不阻塞本提案文档交付。
