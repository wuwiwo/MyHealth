# MyHealth 战斗体验设计提案 v1

> **状态：作者已裁决，可施工；本提案与 `doc/plans/战斗体验施工计划.md` 为当前体验规格。**
> **范围：**重整现有单敌与敌群战斗的演出、战斗反馈、胜负收尾、单场复盘与长期统计体验；不设计新战斗规则。
> **本次文档更新：**只改设计/计划文档，不改运行代码、版本号、缓存戳、README 版本栏或 changelog；后续代码按施工计划逐批执行并遵守发布纪律。
> **事实基线：**现行代码为唯一现状依据。单敌与敌群是两条独立的战斗引擎及渲染管线；不得用一条管线的验收冒充另一条。
> **裁决状态：**体验流程、历史摘要范围、指标与可访问性范围已于 2026-10-09 裁定，见第 8 节；实现顺序与发布边界见施工计划。

---

## 1. 游戏愿景

让移动端 MyHealth 玩家在完成训练后，通过挑战获得一场**看得懂行动与结果、能感受到关键状态变化、结束后能快速复盘并理解长期进步**的 RPG 战斗体验；表现强化必须忠实呈现既有结算事实，不改变战斗结果。

**本提案解决的问题**

- 结算、奖励反馈在战斗结束时并发，注意力被分散。
- 有单位卡、行动横幅、飘字、日志与部分状态徽标，但玩家仍难连续辨认“谁行动、影响谁、发生了什么”。
- 当前有单场群战摘要，但挑战记录没有形成可浏览的战斗历史与趋势。

**设计原则**

1. 先保信息含义与阅读节奏，再做炫目效果。
2. 动画表达已发生的战斗事件；视觉效果不能暗示未发生的命中、暴击、治疗、状态或击杀。
3. 自动快进与逐帧阅读是不同观看模式；速度提高时收缩表现密度，不牺牲结果摘要。
4. 同一体验目标分别落实并验收于单敌与敌群管线。
5. 统计是可追溯的数据视图；口径不确定或无法归因的数据不伪装成精确值。
6. 遵循本轮已裁决的奖励、收尾和数据留存边界；风险明确披露，不因此阻塞已批准范围。

## 2. 核心体验循环

这是**现有挑战循环的体验改造**，不是新增战斗玩法：

1. **选择挑战**：玩家从当前已有入口选择单敌关卡或敌群小关；查看现有关卡与战斗信息。
2. **进行战斗**：引擎照常结算；表现层以行动者、目标和结果为主线呈现关键事件。玩家可以使用该模式已有的手动/自动推进与速度控制。
3. **胜负阶段**：先呈现胜利/失败，不同时铺开奖励明细与统计表；胜负表现结束后进入下一阶段。
4. **战果阶段**：展示并领取奖励与通关变化，奖励只结算一次；战果与详细战绩不在同一视觉层级同时争抢注意力。
5. **战绩与继续**：同一结果面板提供单场摘要及战报入口；玩家可查看后选择下一关、重试或返回。历史统计可在“记录”视图中查看。

**流程裁决（作者确认）**：统一采用“胜负 → 战果 → 战绩/继续”的顺序。胜负阶段 800ms，普通战果阶段 1,200ms，之后自动进入战绩层；奖励先记入原有系统存档，再展示已实际领取结果。详细单场战绩位于独立结果面板区块，不额外强制确认。普通胜负/战果层可用显式“继续”提前推进展示阶段，不支持点背景隐式跳过。敌群胜败都按胜负阶段 800ms → 战果阶段 1,200ms → 结果/战绩层；单敌失败路线即使 auto 开启也关闭 auto，展示 800ms 胜负 + 1,200ms 失败副作用战果，再进入战绩/重试层。单敌自动连战成功时展示胜负 800ms，随后战果至少 2 秒；若期间未被关闭/用户操作取消，则直接进入下一关；自动胜利的战果层提供“查看战绩”，点击会取消推进并立即进入战绩层。阶段推进不依赖 CSS 动画结束事件。失败不自动重试，群战不新增自动连战。异常中止第三结局仅覆盖当前单敌引擎 tick/render 捕获路径；本批不新增群战异常面板或引擎异常行为。此裁决不改变奖励数量和战斗规则。

## 3. 目标用户与平台

- **目标用户**：使用 MyHealth 记录健身并体验 RPG 挑战的个人玩家；主要在手机上进行，兼容桌面浏览器。
- **运行形态**：现有纯前端单页应用、单人回合制挑战；不引入联网对战或服务器权威战斗。
- **设备与输入**：触屏优先，同时兼容鼠标/键盘可用的网页交互。触控热区继续遵循项目现有设计规范。
- **性能目标（本轮验收）**：在 360×640 与 390×844 视口不出现横向溢出、核心单位信息不被裁切、面板互相遮挡或新增浏览器控制台错误；演出不得阻塞战斗继续推进。暂不承诺 60fps 等尚未量测的帧率数字。
- **可访问性**：动画不能是理解事件的唯一通道；需同时提供可读文本/徽标/日志，支持减少动态效果的系统偏好（实现前检查现有支持与影响）。

## 4. 范围

下列 P0 是**本轮施工范围**。每项均给出可验证通过条件；关键阈值已按作者裁决冻结，实施后由主控独立验收。

### P0：本专题体验必须达成

| 特性 | 设计要求 | 可验证验收标准 |
|---|---|---|
| P0.1 行动—目标—结果可读 | 玩家能从一次关键行动的呈现辨认行动者、受影响单位、结果类别及结果值/状态；表现锚定正确目标。 | 单敌与敌群分别选取至少 10 个真实战斗事件样本（含伤害、治疗/护盾、状态变化、击杀/终局；无法触发的事件注明）；至少 8/10 样本在日志不展开时可辨认行动者、目标与结果；事件日志与引擎事件逐项对应，错误目标反馈为 0。 |
| P0.2 状态与护盾即时反馈 | 对已知状态施加/刷新/净化/抵抗/结束以及护盾吸收/破碎，提供语义不同、目标明确的瞬时提示；持续状态可由单位当前标记辨认。未知事件不猜测、不制造反馈。 | 为状态与护盾事件制作“结算事件→表现”映射表；自动化覆盖表内 100% 已支持事件，未知/目标缺失事件不错误挂载；真实浏览器中每类至少演示一个可触发实例，且即时反馈目标与事件 `targetId` / side 一致。 |
| P0.3 按速度组织反馈 | ×1 优先逐事件阅读；更高速档聚合可安全合并的重复结果，保留主要行动、目标、总结果与重要状态/击杀。两个目标或不同语义不得错误合并。 | ×1、×2、×4、×8 的自动化测试分别验证事件顺序/合并口径；引擎日志、HP、胜负和 RNG 输出与基线完全一致（纯表现修改）；真实浏览器每档均无目标误绑、数字与日志冲突、FX 无限残留；具体每档表现窗口在浏览器验收中测量并记录，不另改引擎步进。 |
| P0.4 胜负、奖励、结算不再抢读 | 按已裁决流程依序呈现“胜负 → 战果（奖励/通关变化）→ 战绩与继续”；奖励入账只执行一次，统计在独立区块/详情层。 | 浏览器录制/自动化验证单敌胜利、单敌失败、敌群胜利、敌群失败四条路径：普通胜败路径顺序均为 800ms 胜负 → 1,200ms 战果 → 战绩层；奖励阶段与详细统计不并发抢焦点；奖励与进度只结算一次；单敌自动胜利 800ms 胜负 + 至少 2 秒战果后续关，查看战绩/关闭可打断；失败不自动重试。 |
| P0.5 单场战绩能解释表现 | 单场复盘优先回答“结果如何、贡献来自哪里、关键转折是什么”，并提供可继续查看的战报；现有字段只有在口径可靠时展示。 | 为单敌和敌群分别定义字段字典、归因规则与已知缺失；用固定种子真实战斗核对 UI 每个数值等于所定义事件集合的合计；无事件/不可归因时明确显示 0、未知或不适用，不误导为精确贡献。单敌/敌群分别统计，不对不等价口径做跨模式排名。 |
| P0.6 战斗记录与统计入口 | 玩家能够从挑战的“记录”视图查看战斗相关表现；单场有摘要，长期趋势与训练 PR 分开。 | 独立 store key 持久保存最近 100 场摘要（单敌/敌群合计，FIFO），至少包含时间、模式、关卡、胜负、回合数、可信玩家汇总；挑战记录视图分模式展示场次、胜率、当前/最佳连胜、平均回合及单场贡献。刷新、现有同步及导出/导入保留历史；旧存档无记录时显式空状态，历史容量或统计为零时不能与“无数据”混淆；非法/不可归因字段不得伪装成可信 0。 |
| P0.7 不让演出遮挡或改变玩法 | FX 不遮挡必要信息、日志或操作；不改变伤害、目标、状态时序、胜负、掉落与随机序列。 | 在两个模式、360×640/390×844、抽屉开/关、×1/2/4/8 实测：关键信息遮挡/裁切为 0，触控操作可达；固定种子日志、结果、HP、RNG 与基线逐项一致。 |

### P1：后续迭代（不阻塞 P0）

- 加入音效、震动、镜头/舞台特效；静音和系统减少动态效果偏好须同步设计。
- 更多历史图表、关卡热度图、队伍/宠物构筑对比、可筛选战报。
- 分享复盘卡片、战斗回放或时间轴重播；不在首次改造里扩大数据范围。
- 长期体验研究后再调整奖励动画或失败后建议。

### 明确不做

- 不改伤害公式、命中/暴击契约、技能/状态规则、AI、关卡难度、奖励数量、胜负判定或 RNG。
- 不合并单敌与敌群引擎，也不以改动一套模式代替另一套模式的验收。
- 不为“动画不明显”简单增加全屏粒子、摇屏、颜色闪烁或同时播放音效；不让装饰效果压过目标信息。
- 未经裁决不新增强制点击步骤、不取消用户已有控制、不改变自动模式推进/连战语义。
- 未经裁决不保存完整逐步引擎日志、不改云同步/导入导出协议、不增加无限增长的历史存档。
- 不以插画/新头像/资源采购作为 P0 前置；复用现有单位、宠物、怪物、技能图标与视觉令牌。

## 5. 关卡与内容规模

- 仅针对现有挑战内容与事件，不新增关卡、Boss、敌人、技能、状态或剧情。
- 当前内容规模以运行时配置为准：单敌关卡来自 `page/levels.js`，敌群来自 `page/group-levels.js`。文档历史记录中的章数/大关数可能滞后，不在本提案重述易过期数字。
- 每条渲染管线至少选普通战斗与可触发特殊机制的战斗做浏览器验收；尽量覆盖多目标、护盾、治疗、状态、击杀及环境伤害。若内容无法稳定触发某项，以固定种子或明确标为该路径未验证。
- 战斗事件视觉映射应按**事件语义**而非硬编码关卡名设计；关卡配置只作为验收样本。

## 6. 美术与音频

- **方向**：移动端可读的轻量 RPG 战斗舞台。重点采用行动焦点、目标受击、血条变化、单位状态变化和终局转场来表达因果；保留项目现有深/浅色主题与令牌体系。
- **素材**：优先复用现有怪物头像、宠物头像及技能图标；动效以 CSS/DOM 轻量实现为主。缺少资源时可用简洁的程序化形状或文本标记，不因素材缺口阻断核心信息反馈。
- **音频/震动**：本期 P0 不引入音效、震动或摇屏；无声体验不受影响。后续如加入需另行设计静音与权限。
- **动效约束**：普通事件短且克制；重大事件有层级但不长时间锁住操作；系统减少动态效果时仍能读懂战斗结果。具体时长和振幅需要原型实测，不在文档阶段臆定像素/毫秒常数。

## 7. 输入方案

| 输入 | 动作 | 设计约束 |
|---|---|---|
| 触屏点击 | 选择关卡、切换战斗/日志、手动推进、改变速度、打开/关闭复盘 | 沿用现有入口；新增流程不可误触跳过奖励或复盘；关键按钮热区遵循项目规范。 |
| 鼠标点击 | 与触屏对应的网页控件操作 | 不依赖悬停才出现的关键信息。 |
| 键盘 | 使用现有可聚焦控件的原生激活方式（Enter/Space）；本轮不新增战斗快捷键 | 焦点可见且顺序合理；不发明未实现快捷键。 |
| 系统偏好 | `prefers-reduced-motion: reduce` | 本轮实现：关闭或降低非必要位移/闪烁，保留行动者、目标、结果、状态及胜负文字。 |

> 本专题不新增战斗操作种类；手动/自动和速度档位的行为以现有模式为基线。收尾不新增强制独立确认步骤。

## 8. 风险登记与作者裁决

| 风险 | 影响 | 对策 / 状态 |
|---|---|---|
| 表现“更明显”变成画面更拥挤 | 无法辨认目标和结果，复现原问题 | 先做事件层级与反馈容量规则，再做美化；以关键事件辨认率和遮挡测量验收。 |
| 高速合并丢失语义（例如不同来源伤害、不同目标、护盾与 HP） | FX 与真实结算不一致 | 合并键必须基于目标及事件语义；详细数字/日志继续可查；固定种子验证展示与引擎事件一致。 |
| 单敌和敌群事件模型不同 | 一套“修好”而另一套仍缺反馈 | 分模式列事件映射、分别做浏览器验收；公共规范统一语义，不强行共用引擎或事件结构。 |
| 当前战报存在归因限制（敌群 `gb.log` 行动者按名字归因，同名单位无法完全区分） | MVP、输出/治疗贡献可能归错人 | 本轮不扩展引擎事件 ID；历史数据使用当前可信归因口径并明确披露同名归因限制，不把估算称为精确。稳定 `unitId` 作为后续独立任务。 |
| 单敌与敌群统计口径不能直接比较 | 跨模式趋势失真 | 先分别定义指标与分母；仅比较有共同定义的指标，否则分开展示。 |
| 战斗历史持久保存与同步 | 存储增长、隐私/同步兼容、旧存档迁移复杂度 | 已裁定保存最近 100 场独立摘要并沿现有 store 通用路径同步/导出；先验证配额，写入失败须保留即时结果并提示。 |
| 结算流程改变既有使用习惯 | 改变玩家现有流程与自动连战行为 | 已裁定：按阶段呈现，不新增强制独立确认；单敌自动胜利等待≥2秒，玩家可打断；敌群不新增自动连战。 |
| 用户体验样本量有限 | 小样本不能代表总体满意度或统计显著性 | 本轮按已裁决的每模式 10 样本、8/10 辨识门槛验收；记录条件并明确只代表可用性验证，不推断总体统计结论。 |
| 依赖动效表现的用户可能受减少动态设置影响 | 可访问性模式反馈不足 | 动画之外始终保留文本、状态标记、HP/战报；减少动态效果需纳入同一验收。 |

### 作者裁决（2026-10-09，本轮可施工项已定）

1. **终局流程**：采用“胜负 → 战果（奖励/通关变化）→ 战绩/继续”；奖励先实际入账后展示，奖励不与详细战绩并发抢读。
2. **交互**：不新增强制的独立确认步骤；单敌使用现有结束面板做顺序分层，敌群结果面板分胜负/战果/战绩区块。可以继续、重试或返回。
3. **单敌自动连战**：保留现有自动下一关能力；成功战果至少展示 2 秒后才自动进入下一关，玩家点下一关/关闭可打断；失败不自动重试。敌群本轮不增加自动连战。
4. **战斗历史**：独立 store key 保存最近 100 场摘要（单敌和敌群合计）；FIFO 去旧；跨刷新持久化；随现有 store 自动云同步、导出/导入；不存完整逐步日志、不改同步协议。摘要只纳入有明确统计口径的事件数据，单敌尚不支持的字段显示“不适用”，不得以 0 冒充。
5. **长期指标**：按单敌/敌群分开展示场次、胜率、连胜/最佳连胜、平均回合数；玩家贡献包含输出、治疗、承伤。敌群场地/DOT/护盾单列，暂不跨模式强行横向排名；历史字段详情列在施工计划中。
6. **体验测试阈值**：每模式至少 10 个真实事件样本，至少 8/10 能辨认行动者/目标/结果；浏览器遮挡/裁切为 0。记录实际样本和条件，不把小样本冒充正式统计显著性。
7. **动效与无障碍**：本轮 P0 不引入音效/震动/摇屏；实现 `prefers-reduced-motion` 下的降动效但保留语义反馈，纳入施工验收。

### 剩余风险（不阻塞施工）

- 历史容量 100 场以摘要数据估算；写入前验证 LocalStorage 配额，失败需明确告知并保留本场即时结果，不得静默中断战斗奖励。
- 敌群历史归因当前按行动者名字，同名单位可能无法区分；历史必须披露此限制，稳定事件 ID 留作后续独立改进。
- 动效减少偏好纳入本轮验收；如果浏览器对 CSS 动画、过渡覆盖不一致，须保证语义文本与徽标仍能提供等价反馈并记录兼容性。

### 技术约束

- **不更换引擎**：现项目是原生 JavaScript + HTML/CSS 的浏览器 SPA，没有独立游戏渲染引擎。纯 UI 演出继续使用现有 DOM/CSS；必要时评估少量 Canvas，但不能把它作为信息可读性的替代。
- **保持依赖边界**：单敌逻辑为 `page/battle.js` + `page/game-battle.js`；敌群逻辑为 `page/battle-group.js` + `page/game-render.js`。纯表现任务不得更改引擎输出；两套管线需要各自的测试与浏览器样本。
- **事件为事实源**：展示只消费引擎产生的日志/事件，不从动画反推伤害，也不通过 UI 改变结算。事件缺少稳定目标/来源标识时，先明确兼容和数据模型方案。
- **统计数据**：单场即时结算统计与跨场历史统计分层。历史使用独立 schema key，保留 100 场摘要；云同步/导出走当前通用键机制，容量写入失败需保留已结算的战斗结果并给出提示。
- **浏览器验收**：使用现有测试体系及真实 Chromium；至少覆盖两个模式、窄屏、速度档位、日志抽屉状态、浅/深主题与 `prefers-reduced-motion`。页面隐藏时布局测量无效，浏览器夹具须先进入挑战页并打开战斗视图。
- **施工阶段门槛**：本提案已获批准，按 [战斗体验施工计划](plans/战斗体验施工计划.md) 分批实施。任何线上代码改动须按 `AGENTS.md` bump `APP_VERSION`、同步版本文档与缓存戳、跑测试并提交；当前这次文档提交不 bump。

## 9. 技术约束与完成自检

### 完成自检（答案）

- **一句话能说清体验吗？**能：看懂行动因果、感受到关键状态、结束后能复盘与看见进步。
- **MVP 最小到只剩什么仍有价值？**明确行动者/目标/结果、让状态和护盾变化可读、让终局按阶段呈现、持久保存有界单场摘要并提供分模式长期指标。
- **每个 P0 都可验证吗？**可；表中逐项给出行为、统计、遮挡、基线一致性等条件；体验辨识阈值固定为每模式 10 个样本、至少 8/10 正确。
- **是否把锦上添花误列 P0？**音效、震动、镜头特效、分享回放明确放 P1；不作为核心体验依赖。
- **平台与输入是否匹配？**是；移动优先浏览器，沿用点按、现有手动/自动推进和速度控制；新增流程不依赖悬停或键盘快捷键。
- **哪些决定还答不上？**当前无阻塞性产品裁决项。剩余风险仅为同名单位归因限制、存储配额和样本代表性，已在风险表中登记并有本轮处置办法。
