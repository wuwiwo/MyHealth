## v2.11.1

Date: 2026-10-07

**评审根因 3 + 4 与两处残留（`doc/review-battle-fx-2026-10-07.md`）**

只改 `page/game-render.js` + `page/index.css`；**引擎与固定种子输出逐字节不变**
（108 场 `rowsHash 835214b4…` 与 3 关 `gb.log` SHA256 与 v2.11.0 完全一致）。

### 修复

#### ① 根因 3：状态 / 护盾类事件补**即时语义标记**

评审确认：`gbParseHit` 只认 damage/heal/terrain/dot，对 `type:'status'` 直接返回 null →
**护盾吸收、护盾破碎、破甲、中毒、冰冻、潮湿、睡眠、嘲讽、净化、末日、幽魂附身、威吓、变小、蓄力**
全都没有即时反馈，只能去战报里找。

修法：新增**显式小表** `GB_FX_MARKS` + `gbMarkerFor(e, parsed)` —— 匹配到已知文案就出一条短标记
（如护盾吸收 → `🛡️120`），**匹配不到什么都不出**（不猜、不造噪声，有反向断言）。
标记同样走 `gbFxFloat`：一起参与**目标锚定**、跨步占位与档位生命期。

#### ② 根因 4：受击反馈从「重启关键帧动画」改为「状态高亮」

评审确认：单位芯片每步 `innerHTML` 重建，动画类挂在新节点上会**从头再播** →
高速档位表现为「不断重启 / 一直亮着」，闪烁失去语义。

修法（`page/index.css`）：`.gb-unit.gb-hit` 由 `animation:gbHit .4s` 改为
`box-shadow + filter` 的**状态**（配 `transition`）—— 重建后的新节点仍是「亮着」，不重播时间轴；
`@keyframes gbHit` 保留（兼容既有引用）。`gb-hit` 类名不变（既有断言 `enemy-1:gb-hit` 仍守）。

#### ③ 残留 A：四槽横向加宽（默认布局自身重叠 288px² → 0）

`GB_FX_SLOT_OFF` 由 `[[0,0],[-46,-18],[46,-18],[0,-36]]` 改为 `[[0,0],[-78,-18],[78,-18],[0,-70]]`：
横向 ±46 < 飘字盒宽 70 → 相邻槽必然重叠（实测 288px²）；加宽到 ±78 后横向分离，
slot3 纵向 -34 → -70（同列要 |Δy| ≥ 上浮 34 + 盒高 30 = 64 才不叠）。
⚠️ **坐标契约随之更新**：§13 期望值改为 `200,580 | 122,562 | 278,562 | 200,510`（§19 同步），
并把原「4 槽自身仍有小面积重叠」的**如实记录断言翻转为「不再重叠」**。

#### ④ 残留 B：占位兜底驱逐（**未达成目标，如实报告**）

`_gbFxFindFreeSpot` 找不到空位时返回 null，`gbFxFloat` 调用新增的 `gbFxEvictColliding`
驱逐冲突的前序飘字（新信息优先）。**单元测试层面按预期工作**（§23(d) 断言驱逐发生），
但**真实浏览器复测显示该指标反而变差**：

| 指标（390×844，独立夹具，种子 4242） | v2.11.0 | **v2.11.1** |
|---|---|---|
| 跨步 live 重叠 max | 108px² | **660px² ❌ 变差** |
| 同一步内两两重叠 | n=364 / max 1650px² | n=239 / max 1650px²（对数减少） |
| 施法 × 飘字相交 | 0 | **0 ✅ 无回归** |

⇒ **残留 B 未解决、且我的驱逐策略疑似有害**。建议下一步**先回退驱逐**（保留 ①②③ 三项已验证的改进），

## v2.11.0

Date: 2026-10-07

**战斗演出可读性：演出吞吐随档位收缩 + 数字绑定目标（评审根因 1 + 2）**

只改 `page/game-render.js` 的演出层；**引擎与固定种子输出逐字节不变**
（108 场 `rowsHash 835214b4…` 与 3 关 `gb.log` SHA256 与 v2.10.1 **完全一致**）。

### 修复

#### ① 根因 1：演出生命周期与逻辑步进不匹配（「看不清」的第一性原因）

**评审实测口径**：群战飘字/施法固定 **900ms**，而速度档位只压缩**事件间隔** →
同时在场批次 = 900 ÷ 步进 = ×1 **1.29** / ×2 **2.57** / ×4 **5.14** / ×8 约 **9~10** 批。
这不是「动画不好看」，而是数字以 5~10 倍密度堆在同一小块区域。

**修法**：新增 **`gbFxPolicy(speed)`** 演出策略表 —— 把演出生命周期与**演出窗口**显式绑定：

| 档位 | 步进（实测/名义） | 生命期 | 聚合同目标 | 受击闪烁 | 施法文案 |
|---|---|---|---|---|---|
| ×1 | 700ms | **900ms**（不变，不牺牲慢速观感） | ✗ 逐事件 | 900ms | ✓ |
| ×2 | 350ms | **700ms** | ✓ | 600ms | ✓ |
| ×4 | 175ms | **340ms** | ✓ | 260ms | ✗（原有） |
| ×8 | ~88ms | **210ms** | ✓ | 160ms | ✗（原有） |

- **聚合**（×2 起）：同一步内**同一目标**的同类事件合并成一条飘字，数值为**和**
  （老实现：一步打同一目标 3 次 = 3 条挤在同一位置；现在 1 条 `-300`）。
- 生命期同时写进 `setTimeout` 与**内联 `animationDuration`**，动画不会被截断。
- 受击闪烁 `flashMs = min(gbHitFlashMs(), pol.flashMs)` —— 高档位收窄到约 1 个窗口，
  不再是「一直亮着」（v2.8.0 的记忆窗口保留为下限保护）。

#### ② 根因 2：飘字脱离目标锚点（「看不懂发生了什么」的原因）

**评审结论**：v2.4.2 起数字统一锚在中央线 `#gbArenaMid`，与「谁挨打」只剩芯片闪烁一条联系，
AOE 打 5 个目标时无法逐一对应。

**修法**：`gbFxFloat` 新增**显式横向锚点**参数，`playAttackFeedback` 用 `gbCardForEvent` 取目标芯片的
`getBoundingClientRect()` 中心 x 作为锚点 → **数字横向落在被打单位正下方**（保留中央带，不挤芯片；
取不到芯片 rect 时退回中央区中心）。⚠️ 有锚点时**不再叠加横向槽位偏移**（横向位置从此是语义信息），
只保留纵向错位防同目标叠字。

### 新增功能

无（两条都是评审定位的根因修复）。

### UI 调整

- 高速档位（×2/×4/×8）数字不再堆叠成团：同目标伤害合并、生命期收窄到约 1~2 个演出窗口。
- 伤害数字横向对齐到被打的单位（AOE 时能一眼看出「谁掉了多少」）。
- ×1 行为**刻意保持**（逐事件、900ms 生命期），慢速观感不变。
