### 新增功能

**① 原型归纳（本版的核心决策）**

`page/levels.js` 有 33 章 × 6 关 = **189 个唯一敌人名**，`page/group-levels.js` 另有敌群名字池 **21 名**。
**不做逐名绘制**，改为归纳为 **18 个视觉原型**（Archetype），敌人名经确定性映射落到原型上。

不做 189 枚的两条硬伤（写入 `doc/design-monster-icons.md` §0）：

1. **去重目标结构性地无法达成** —— 189 个名字里大量在 16×16 下必然视觉同构
   （`永恒壁垒` / `终极壁垒` / `星核壁垒` / `冥河壁垒` / `永夜壁垒` / `太初壁垒` …），
   逐名分配只会产出十余枚几乎一样的方盾。
2. **无法维护** —— 项目仍在扩章（`GROUP_MAX` 18→21→24，`levels.js` 已到 chap33）。
   逐名映射意味着每加一章都要新画图标；原型映射下**新增关卡自动复用就近原型**。

原型的划分依据是**真实数据规律**而非拍脑袋：`levels.js` 从 chap6 起命名严格按**槽位分工** ——

| 槽位 | 命名范式 | 原型 |
|---|---|---|
| 1 | `X守卫` / `X哨卫` / `X先锋` / `X行者` | guard / ranger / sentinel |
| 2 | `X刺客` / `X猎手` / `X猎影` | assassin / ranger |
| 3 | `X巨像` / `X壁垒` / `X巨兽` | golem / beast |
| 4 | `X骑士` / `X剑圣` / `X剑帝` / `X巨人` | rider / knight / titan |
| 5 | `X法师` / `X使者` / `X化身` / `X代言` | mage / lord / avatar |
| 6 | `BOSS X` | lord / dragon / eyeboss / avatar |

槽位只用来确定**候选集合**，最终裁决由关键字完成。**覆盖验证：18/18 原型被命中，
189/189 关卡 + 21/21 敌群名全部映射成功，无悬挂原型、无未分类名字。**

**③ 新增模块 `page/monster-archetype.js`（图标渲染唯一入口）**

- `MONSTER_ARCHETYPES`（18 原型表）· `MONSTER_ARCHETYPE_FALLBACK`（兜底原型 `sentinel`）
- `monsterArchetypeOf(name, boss)` —— 名字 → 原型 id，判定顺序**严格自上而下、首个命中即返回**
  （顺序本身是规格的一部分，改动会改变大量关卡的图标）
- `monsterArchetypeOfLevel(lv)` —— 直接吃 `levels.js` 的关卡对象
- `monsterIconUrl()` / `monsterIconHtml()` / `monsterIconHtmlByName()` / `monsterIconHtmlByLevel()`

  `'精英·狂战'` / `'杂兵·剑'` 两类写法
- **BOSS 判定只认 `boss:true` 字段**，不靠名字前缀猜（`'BOSS 万古长夜'` 与同章 `'万古守望'` 相邻，前缀会有歧义）

三处均为**纯展示层改动，零数值影响**：未动任何战斗 / 经济 / 存档口径。

**⑤ 测试：新增 `scripts/test-monster-icons.js`（357 断言）**

守六件事：

1. **映射全覆盖** —— 189 关 + 21 敌群名全部映射到有效原型，无 `undefined`、无异常
   （映射漏了某个名字时界面只是空白头像、**不会报错**，属静默降级，故必须有断言）
2. **无悬挂原型** —— 每个原型至少被 1 个真实敌人名命中（防「画了没人用」）
3. **资源存在且合规** —— 18 个原型各有同名 SVG 且满足硬规格
   （**代码里路径写对了 ≠ 文件真的在** —— 本项目有过 v2.0.3 / v2.0.4「模块挂上了但界面上看不见」的事故）
4. **缺图标不炸** —— 非法原型 id → `null` / `''`；**未知敌人名走兜底原型而不是 `null`**
   （界面不能因为策划加了个新名字就出现空白头像）
5. **唯一入口** —— `'media/monsters/'` 字面量只允许出现在 `monster-archetype.js` 一处
6. **三处调用点真的接上了** + CSS 契约（`.mon-ico` 必须带 `image-rendering:pixelated`）
   + `index.html` 引入顺序（必须在 `levels.js` **之后**）

**⑥ 设计分工（双子代理并行 + 交叉复核）**

| 子代理 | 模型 | 负责 |
|---|---|---|
| A | `deepseek-v4.1-flash` | 人形组 9 个（soldier / guard / berserker / sentinel / bow / ranger / assassin / knight / rider） |
| B | `hy4` | 非人形组 9 个（mage / golem / titan / beast / undead / dragon / eyeboss / lord / avatar） |

分组的依据：A 组全部为「正面/侧面直立人形」，共用同一套身体比例，
**内部必须靠「持什么武器 / 戴不戴盔 / 露不露脸」区分**，是难度更高的一组；
B 组全部为非人形，轮廓本身差异巨大（三角帽 / 方块 / 倒三角 / 四足 / 骷髅 / 长颈带翼 / 纯眼球 / 冠冕袍服 / 菱形核心），
组内自然去重。这样分配避免「A 组画到第 9 个已经分不清 soldier 和 knight」集中在同一侧。

### 设计口径修订（本版新增的两条硬指标）

**① 深色主题可读性**（`doc/design-monster-icons.md` §1.3，本套新增）

应用默认主题为**深色**，卡面底色 `#111827`。宠物套的 `darkcrow` 曾在 v2.2.29 踩过隐形
（主体 `#0B0D12` 对卡面只有 **1.10:1**，几乎不可见）。

本套要求：**每个图标在深色卡面 `#111827` 与浅色卡面 `#ffffff` 之下，各自都至少有一种颜色达到 3:1。**

> ⚠️ **两种主题允许用不同的颜色。** 初版把这条误写成「同一颜色必须同时满足两边」，
> 经验证**过严**：深色卡面要求颜色够亮、浅色卡面要求颜色够暗，除中间灰外没有颜色能两边都达 3:1，
> 会误杀「亮主体 + 深描边」这类完全正确的设计（宠物套 `sparkle` 即是：亮黄主体在深色下 11.22:1、
> 深色描边在浅色下 15.13:1，两边都成立）。**已修正判据与文档。**

**② 主体包围盒 ≥ 30×30 px** —— 沿用宠物套 §1.4，本套严格执行（`berserker` 即因 27 格宽被打回）。

### 已知取舍（记录，未处理）

- 原型映射是**启发式**：关键字规则覆盖了全部 189 个现有名字，但未来新增命名范式
  可能落到兜底原型 `sentinel`。兜底保证**不出现空图标**，但造型可能不贴切 ——
  新增章节后建议跑一次 `test-monster-icons.js` 看原型分布是否出现异常堆积。
- `soldier` 原型承载 27 关（占比最高）。这是「泛用步兵」的必然结果，
  但意味着这 27 关联的视觉差异化主要靠**关卡名文字**而非图标。
- `bow` 只命中 1 关（`2-2 弓弩手`）。保留它是因为「弓」在轮廓上与 `ranger`（游侠）差异足够大，
  不值得为省一枚图标而合并。
